# راهنمای عمومی ساخت برنامه‌های وب فارسی و ماژولار

این سند یک الگوی عمومی برای طراحی، توسعه، تست و انتشار برنامه‌های وب سازمانی است. این راهنما به پروژه یا فناوری خاصی وابسته نیست و باید در پروژه‌های جدید نیز مبنا قرار گیرد.

## 1. اصول پایه

- برنامه به‌صورت Web Application و قابل اجرا در مرورگر ساخته شود.
- رابط کاربری، API، منطق کسب‌وکار، پایگاه‌داده و تنظیمات از هم جدا باشند.
- ساختار برنامه ماژولار باشد؛ افزودن ماژول جدید نباید باعث تغییر گسترده در ماژول‌های قبلی شود.
- هر ماژول مرز، مسئولیت، مسیرهای API و مستندات مشخص داشته باشد.
- تصمیم‌های مهم فنی در مستندات ثبت شوند.
- قابلیت‌های غیرمرتبط در یکدیگر ادغام نشوند.

## 2. رابط کاربری فارسی و RTL

- ریشه HTML شامل `dir="rtl"` و `lang="fa-IR"` باشد.
- تمام متن‌های قابل مشاهده برای کاربر فارسی و قابل فهم باشند.
- از فونت محلی و خوانای `Vazirmatn` استفاده شود؛ برنامه نباید برای فونت یا فایل اصلی به CDN وابسته باشد.
- نمایش اعداد، تاریخ شمسی، واحدها و متن‌های ترکیبی فارسی/انگلیسی کنترل‌شده باشد.
- جهت آیکن‌ها، فاصله‌ها، جدول‌ها و فرم‌ها با RTL سازگار باشد.
- طراحی برای دسکتاپ، تبلت و موبایل واکنش‌گرا باشد.
- وضعیت‌های Focus، Hover، Disabled، Loading، Success، Warning و Error مشخص باشند.
- همه قابلیت‌ها تا حد امکان با صفحه‌کلید نیز قابل استفاده باشند.
- کنتراست، اندازه متن، هدف لمسی و ترتیب Focus بر اساس WCAG 2.2 سطح AA بررسی شوند.

## 3. طراحی تجربه کاربری

- در هر صفحه اقدام اصلی کاربر باید واضح باشد.
- صفحه نباید با کنترل‌های غیرضروری شلوغ شود.
- عملیات طولانی Progress، وضعیت جاری و امکان لغو داشته باشد.
- پیام خطا علت، اثر و راهکار بعدی را به زبان ساده توضیح دهد.
- شکست عملیات نباید نتیجه معتبر قبلی را بی‌دلیل حذف کند.
- عملیات حساس مانند حذف، ارسال مجدد یا تحلیل مجدد نیازمند تأیید کاربر باشد.
- فرم‌ها اعتبارسنجی سمت کاربر و سمت سرور داشته باشند.
- تعداد واقعی داده‌ها، موارد انتخاب‌شده و نتیجه فیلترها نمایش داده شود.

## 4. معماری فنی

- Frontend و Backend از طریق API مشخص با هم ارتباط داشته باشند.
- منطق کسب‌وکار داخل UI یا Controller پراکنده نشود.
- هر لایه فقط مسئولیت خود را انجام دهد.
- وابستگی‌ها صریح، نسخه‌بندی‌شده و قابل نصب مجدد باشند.
- تنظیمات محیطی از کد جدا باشند.
- محیط‌های Development، Test و Production از هم تفکیک شوند.
- اجرای عملیات سنگین در Worker، Queue یا پردازش پس‌زمینه انجام شود تا رابط کاربری قفل نشود.
- عملیات باید قابل تکرار، قابل لغو و در صورت امکان Idempotent باشد.

## 5. API و قرارداد داده

- API با OpenAPI مستند شود.
- برای هر Endpoint روش HTTP، ورودی، خروجی، خطاها، احراز هویت و نمونه درخواست/پاسخ ثبت شود.
- قرارداد API نسخه‌بندی شود و تغییر ناسازگار بدون اعلام قبلی انجام نشود.
- پاسخ‌ها ساختار یکنواخت داشته باشند؛ برای خطا حداقل `code`، `message` و جزئیات قابل پیگیری ارائه شود.
- اعتبارسنجی Schema در سمت سرور الزامی است.
- Pagination، Filter، Sort و Search برای مجموعه‌های بزرگ پیش‌بینی شود.
- تاریخ‌ها در API قالب مشخص داشته باشند؛ تبدیل به تاریخ شمسی در لایه نمایش انجام شود.
- Timeout، Retry محدود و رفتار قطعی در برابر خطاهای شبکه تعریف شود.

## 6. امنیت

- امنیت از مرحله طراحی در نظر گرفته شود، نه فقط هنگام انتشار.
- احراز هویت، نشست، سطح دسترسی و کنترل دسترسی هر Endpoint مشخص باشد.
- ورودی‌ها اعتبارسنجی و خروجی‌ها متناسب با Context پاک‌سازی/Encode شوند.
- SQL Injection، XSS، CSRF، SSRF، Path Traversal و خطاهای مجوز بررسی شوند.
- رمز عبور و کلید API هرگز در Git، فایل Frontend، Log یا پیام خطا قرار نگیرند.
- Secretها از Environment Variable، Secret Manager یا محل امن خوانده شوند.
- ارتباط‌های حساس از HTTPS استفاده کنند.
- لاگ‌ها اطلاعات محرمانه، Token و رمز عبور را ثبت نکنند.
- برای برنامه‌های وب، OWASP ASVS 5.0 به‌عنوان چک‌لیست امنیتی استفاده شود.

## 7. داده و پایگاه‌داده

- مدل داده، رابطه‌ها، محدودیت‌ها و Indexها مستند باشند.
- تغییرات Schema با Migration نسخه‌بندی شوند.
- عملیات چندمرحله‌ای حساس داخل Transaction انجام شود.
- داده‌های خام، داده‌های پردازش‌شده و Cache از هم تفکیک شوند.
- حذف داده تا حد امکان قابل بازیابی یا Auditپذیر باشد.
- Backup، Restore و نگهداری داده آزمایش شوند.
- داده‌های بزرگ با Pagination و Query بهینه خوانده شوند.
- تاریخ ایجاد، آخرین تغییر و منبع داده برای رکوردهای مهم نگهداری شود.

## 8. ماژولار بودن

ساختار پیشنهادی:

```text
frontend/
  modules/
    module-a/
    module-b/
  shared/
backend/
  modules/
    module_a/
    module_b/
  shared/
database/
docs/
tests/
config/
```

- Sidebar ابتدا فهرست ماژول‌ها را نشان دهد.
- پس از انتخاب ماژول، فقط قابلیت‌های همان ماژول نمایش داده شوند.
- ماژول‌ها نباید مستقیماً به جزئیات داخلی یکدیگر وابسته باشند.
- اجزای عمومی مانند جدول، فرم، پیام، Dialog و دسترسی در Shared قرار گیرند.

## 9. کارایی و مقیاس‌پذیری

- داده‌ها فقط در زمان نیاز خوانده شوند.
- Queryهای غیرضروری، واکشی تکراری و N+1 Query حذف شوند.
- Cache با کلید، مدت اعتبار و روش Invalid‌سازی مشخص استفاده شود.
- عملیات حجیم Batch و قابل مشاهده باشند.
- برای درخواست‌های خارجی Timeout مشخص و Retry محدود وجود داشته باشد.
- منابع، Connection و Workerها به‌درستی آزاد شوند.
- Startup سریع باشد و بارگذاری غیرضروری هنگام ورود انجام نشود.

## 10. خطا، لاگ و مشاهده‌پذیری

- خطاها در مرزهای مشخص مدیریت شوند.
- پیام کاربر از جزئیات فنی داخلی جدا باشد.
- هر خطای مهم شناسه پیگیری داشته باشد.
- Log سطح‌بندی‌شده باشد: Debug، Info، Warning و Error.
- رویدادهای مهم با زمان، کاربر، عملیات و نتیجه ثبت شوند.
- Health Check برای سرویس‌های اصلی وجود داشته باشد.
- خطاهای خارجی مانند 401، 403، 404، 408، 429 و 5xx رفتار جداگانه داشته باشند.

## 11. تست و تضمین کیفیت

- تست واحد برای منطق کسب‌وکار و توابع حساس نوشته شود.
- تست API قرارداد ورودی/خروجی و خطاها را بررسی کند.
- تست یکپارچه ارتباط پایگاه‌داده و سرویس‌های اصلی را پوشش دهد.
- تست UI سناریوهای اصلی کاربر را بررسی کند.
- تست RTL، فونت فارسی، متن‌های طولانی و اندازه‌های مختلف صفحه انجام شود.
- سناریوهای بدون داده، داده ناقص، شبکه قطع، Timeout، لغو و دسترسی غیرمجاز تست شوند.
- قبل از انتشار، تست‌ها به‌صورت خودکار اجرا شوند.
- هیچ قابلیت جدیدی بدون تست مناسب و مستندات مرتبط ادغام نشود.

## 12. Git و فرایند توسعه

- کد در Git نگهداری شود.
- برای هر قابلیت یا اصلاح مهم Branch جدا ایجاد شود.
- Commitها کوچک، اتمیک و با پیام روشن باشند.
- قبل از ادغام، Diff و تست‌ها بررسی شوند.
- تغییرات نامرتبط در همان Commit وارد نشوند.
- Tag یا Release نسخه‌گذاری‌شده ایجاد شود.
- امکان Rollback به نسخه پایدار قبلی وجود داشته باشد.

## 13. تنظیمات و انتشار

- تنظیمات قابل انتقال از کد جدا باشند.
- فایل نمونه مانند `.env.example` یا `config.example.json` بدون Secret ارائه شود.
- نصب وابستگی‌ها و اجرای برنامه مستند باشد.
- Build قابل تکرار باشد.
- نسخه، تاریخ انتشار و Changelog ثبت شود.
- خروجی Production از Debug و Secretها پاک باشد.
- استقرار روی سرور داخلی یا ابری بدون تغییر اساسی در کد امکان‌پذیر باشد.

## 14. مستندات الزامی

- ساختار پوشه‌ها
