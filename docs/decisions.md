# تصمیم‌های معماری (ADR log)

این فایل تاریخچه تصمیم‌هاست. تصمیم قبلی حذف نمی‌شود؛ اگر تغییر کرد، یک ADR
جدید با وضعیت `Supersedes` اضافه می‌شود.

## ADR-001 — Desktop WebView2 + Python Bridge

- وضعیت: Accepted
- تاریخ: 2026-08-25
- تصمیم: UI با HTML/CSS/JavaScript و منطق با Python اجرا شود؛ ارتباط فقط از
  `bridge.Api` انجام شود.
- دلیل: استفاده مجدد از منطق Python، اجرای آفلاین، Build ساده EXE و UI قابل
  توسعه.
- پیامد: قرارداد Bridge باید پایدار و مستند باشد.

## ADR-002 — Pipeline مستقل از UI

- وضعیت: Accepted
- تصمیم: بارگذاری، Rule Engine، Scoring و گزارش‌ها در ماژول‌های Python مستقل
  بمانند و Bridge فقط orchestration و serialization انجام دهد.
- دلیل: تست‌پذیری و امکان اجرای تحلیل بدون WebView.

## ADR-003 — دو Mode مستقل تحلیل

- وضعیت: Accepted
- تصمیم: `comparison` و `general` مسیرهای مستقل در Pipeline هستند. تحلیل کلی
  با دو دوره صوری پیاده‌سازی نمی‌شود.
- دلیل: جلوگیری از وابستگی State و فیلترهای دوره‌ای قبلی.

## ADR-004 — N/A به‌جای حدس

- وضعیت: Accepted
- تصمیم: شواهد ناکافی، نبود Task غیرضروری و پاسخ AI بدون امکان امتیازدهی باید
  N/A شوند، نه صفر یا Penalty.
- دلیل: حفظ اعتبار ارزیابی و جلوگیری از تنبیه مواردی که داده کافی ندارند.

## ADR-005 — کلید API خارج از Repository

- وضعیت: Accepted
- تصمیم: API key در SQLite یا فایل رمزنگاری‌شده محلی ذخیره شود و در Export
  تنظیمات وارد نشود.
- دلیل: جلوگیری از نشت Secret در Git و فایل‌های انتقالی.

## ADR-006 — Cache قابل اعتبارسنجی

- وضعیت: Accepted
- تصمیم: Cache فقط وقتی موفق است که برای معیارهای مورد انتظار، پاسخ قابل
  اعتبارسنجی داشته باشد؛ پاسخ N/A معتبر نیز قابل Cache است.
- دلیل: جلوگیری از نمایش نتیجه قدیمی/خالی به‌عنوان تحلیل موفق.

## ADR-007 — نسخه‌بندی و Release

- وضعیت: Accepted
- تصمیم: تغییرات روی `GapCode` انجام شوند؛ نسخه در `VERSION`، تاریخچه در
  `CHANGELOG.json` و Build خروجی در EXE محلی ثبت شود.
- دلیل: امکان تست، بازگشت به نسخه قبلی و تحویل قابل تشخیص.
